# Smithery Deployment Flow

This project generates a hosted MCP endpoint from the customer’s product API.
Smithery publishing happens after the MCP release is generated and tested.

## What the user sees in Step 4

Step 4 now shows three deployment values:

1. **Public MCP URL for Smithery**
   - This is the URL Smithery should publish.
   - It is generated by the backend from:

     ```text
     PRODUCT_TO_MCP_PUBLIC_BASE_URL/mcp/{deployment_slug}/mcp
     ```

2. **Local testing URL**
   - This is useful only while testing locally through Vite/backend proxy.
   - Localhost URLs cannot be published to Smithery.

3. **Release identity**
   - Shows the release id and manifest hash for support/debugging.

## What the customer must provide

To publish into their Smithery account, the customer needs to provide:

- Smithery namespace or organization name, for example `@acme` or `acme`;
- server name/slug, for example `demo-store-mcp`;
- Smithery API key;
- permission to publish/update that server in their Smithery namespace.

The Smithery API key is submitted once from the UI to the backend publish
endpoint. The prototype clears the browser input after submit and should not
persist a broad Smithery key.

## What our backend must provide

Before Smithery deployment works in production, the backend must be deployed
behind public HTTPS and configured with:

```text
PRODUCT_TO_MCP_PUBLIC_BASE_URL=https://your-backend-domain.com
PRODUCT_TO_MCP_SMITHERY_API_URL=https://api.smithery.ai
```

Smithery requires a public Streamable HTTP MCP URL. A local URL such as
`http://127.0.0.1:8000/...` is only for development and will not work for
Smithery publishing.

## Backend publish flow

```text
User generates release
  -> backend stores immutable release manifest
  -> backend computes public MCP URL
  -> user enters Smithery namespace/server/API key
  -> backend submits release to Smithery
  -> Smithery returns deployment id, status, warnings, and Smithery MCP URL
  -> UI shows the returned Smithery URL/status
```

## Smithery requirements checked from docs

- URL publishing expects a public MCP server URL.
- The server should expose Streamable HTTP transport.
- If auth is required, the server needs OAuth-compatible behavior.
- Smithery scans the endpoint to read metadata/tools.
- Smithery API publishing uses a Bearer API key and a qualified server name.

For the prototype, we support the URL publishing path first because our system
already hosts generated MCP endpoints. Hosted JavaScript module uploads and
MCPB bundle publishing can be added later if needed.

## Current prototype status

Implemented:

- release-specific MCP endpoint generation;
- backend Smithery publish endpoint;
- frontend Step 4 Smithery deployment panel;
- UI display for public MCP URL, local testing URL, release id, and manifest;
- publish result display for Smithery status, deployment id, warnings, and URL.

Still needed for production:

- real hosted backend URL with HTTPS;
- OAuth or access-control layer for public MCP callers;
- static server card endpoint if Smithery scanning needs manual metadata;
- persisted Smithery deployment records and status polling;
- rollback/re-publish workflow;
- customer account/team ownership model;
- audit logs around publish actions.
